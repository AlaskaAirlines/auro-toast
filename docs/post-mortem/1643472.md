# AB#1643472

## Executive Summary

Tapping the "close" button on a toast notification could silently tell the app it had been closed *twice* instead of once, about a third of a second apart. This was first reported on phones and other narrow screens, but further review found the same double-notification could also happen on a normal desktop-sized screen, if the close button was tapped while a toast was in the middle of automatically fading away on its own. Most of the time this was invisible to guests, but any feature reacting to a toast closing (analytics logging, removing an item from a list, re-enabling a button) could run twice for a single close. This change makes closing a toast — at any screen size, and however it's closed — behave the same way every time: once, and only once. See [AB#1643472](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1643472).

## The Problem

Below a certain screen width (roughly phone- and small-tablet-sized), auro-toast has always let a guest dismiss a toast by tapping anywhere inside it, not just the close button — a convenience for touch devices. That convenience feature was not aware that a tap could also land on the dedicated close button, which already has its own, independent way of closing the toast. So a single tap on the close button, on a narrow screen, triggered both closing mechanisms at once — one instantly, and one about 300 milliseconds later.

Separately — and at **any** screen width, not just narrow ones — every toast that auto-hides fades itself out over roughly a third of a second before it actually closes. If a guest manually clicked the close button during that fade-out window, the close button's own immediate close and the fade-out's own scheduled close could both go on to fire, again about 300 milliseconds apart. This second path has nothing to do with screen width; it reproduces on a full-size desktop screen just as easily as on a phone. Either way, any code elsewhere in an app that listens for "the toast was closed" would hear about it twice.

## Root Cause

Two distinct, independently-triggerable causes existed in `src/auro-toast.js`, both stemming from the same underlying gap: `fadeOutToast()` scheduled its call to `closeToast()` in an **untracked** `setTimeout(..., 300)` whose id was never stored, so nothing could cancel it once scheduled.

1. **Width-independent race (any viewport):** `fadeOutToast()` is also how the auto-hide timeout closes a toast — after the auto-hide delay elapses, it adds a `.hidden` CSS class and schedules the untracked close 300ms later. If a guest clicked the close button during that 300ms window, `clickToClose()` closed the toast immediately, but had no way to cancel the still-pending, unstored timer — which fired `closeToast()` a second time regardless of width.
2. **Mobile-only compounding cause (<767px):** below the mobile breakpoint, a host-level `onclick` handler installed by `setOnClick()` (to let guests tap anywhere on the toast to dismiss it) also called `fadeOutToast()`. Because the close button lives in a shadow DOM and its click event is `composed`/bubbling, a tap on the close button triggered `clickToClose()` (button-level listener) *and* bubbled up to this host `onclick`, which scheduled a second untracked close via the same unstored-timer gap as above — on top of the width-independent race, not instead of it.

Both causes dispatched their duplicate close through the same unstored `setTimeout`; fixing the timer-tracking gap (below) closes the width-independent race directly, and closes the mobile-specific path once the tap-to-dismiss handler is also taught to recognize a close-button tap as already handled.

## The Fix

- Added a tracked `closeTimer` field (previously the `fadeOutToast()` → `closeToast()` delay was an anonymous, unstored `setTimeout`), cleared alongside `fadeOutTimer` in `clickToClose()`, `closeToast()`, `disconnectedCallback()`, and the `variant`-change branch of `updated()`.
- `closeToast()` now guards against re-entry: it returns immediately if the toast isn't currently `visible`, so a second call (from any source) after the toast has already closed is a no-op.
- `fadeOutToast()` only proceeds (adds the `.hidden` class, schedules a close) if the toast is still `visible`.
- Root-caused the mobile double-close directly: `setOnClick()`'s host-level handler now inspects `event.composedPath()` and does nothing if the click originated on the close button — `clickToClose()` already owns that case, so the tap-to-dismiss handler no longer runs at all for close-button taps, rather than relying solely on the `visible` state guard to suppress the resulting duplicate.
- Added `disconnectedCallback()` to clear both timers on unmount, so a detached toast can't fire a delayed close on a node no longer in the document.
- Extracted a `_scheduleAutoHide()` helper (called from both `connectedCallback()` and `updated()`) so the auto-hide countdown correctly re-arms if a toast is disconnected and later reconnected (e.g. re-parented elsewhere in the DOM) — `updated()` alone does not re-run on reconnect, since no reactive property changes as a result.
- Cancelling a pending fade-out on a `variant` change now also removes the `.hidden` class from the toast container, so an interrupted fade doesn't leave the toast stuck invisible while still marked `visible`.

## Why This Works

The fix was arrived at over three review passes, each independently verified rather than trusted on inspection:

1. **Initial fix** (timer tracking + re-entry guard + `composedPath()` root cause) was paired with a regression test simulating a mobile-width close-button tap. A code review agent (dual-model, opus + sonnet) caught that the test used the `disableautohide` attribute, which made `fadeOutToast()` short-circuit *before* reaching the new `visible` guard — the test passed even against the unfixed source. This was confirmed empirically (reverting the source fix made the test fail as expected; restoring it made the test pass), not just reasoned about, and fixed by removing `disableautohide` from the test fixture.
2. **Follow-up hardening** (from the same review's recommendations): added `disconnectedCallback()` timer cleanup, the `composedPath()` root-cause fix, and replaced a brittle `Object.defineProperty(window, "innerWidth", ...)` test stub with a proper `sinon.stub(window, "innerWidth").get(...)` that correctly restores the original accessor.
3. **A second review pass** (also dual-model, high effort) on that follow-up work caught two *new* regressions it had introduced: clearing `closeTimer` on a `variant` change without undoing the `.hidden` class (a permanently stuck, invisible toast), and adding `disconnectedCallback()` without a matching re-arm in `connectedCallback()` (auto-hide permanently disabled after any reconnect). Both were fixed, covered with new regression tests, and each test was individually verified to fail against the pre-fix code and pass against the fix — the same discipline applied the first time.
4. **A human review pass** correctly challenged the scope of the fix itself: the double-dispatch was documented (both in this file and the original ticket) as mobile-width-only, but the reviewer had independently reproduced it at desktop width via a close-button click during the auto-hide fade-out, and by calling `closeToast()` three times directly. Both scenarios were re-verified from scratch against this fix — new tests for each were confirmed to fail against the pre-fix source and pass against the fix — before concluding the already-committed fix covered them (the same `closeTimer` tracking and re-entry guard happen to be width-independent, even though the accompanying test coverage at the time was mobile-only). This file's scope was corrected accordingly.

The `composedPath()` approach is preferred over relying solely on the `visible` state guard because it removes the double-invocation at its source (the host handler never runs for close-button clicks) rather than suppressing a symptom of it — which also closes a latent race where a consumer's `toast-close` listener synchronously re-showing the toast could have defeated a state-only guard.

## Outcome

Closing a toast — however it's closed, and at any screen size — now notifies the rest of the app exactly once. This covers both the originally-reported mobile close-button tap and a second, independently-discovered desktop-width case (closing manually during the auto-hide fade-out). Toasts also no longer get stuck permanently invisible if their severity/type changes while they're in the middle of fading out, and they continue to auto-dismiss correctly even if a toast is moved to a different part of the page while visible.

## Ticket Completeness

4 of 4 acceptance criteria resolved. The ticket itself was scoped to the mobile-width (<767px) symptom; a subsequent review correctly identified that the same underlying untracked-timer defect also reproduces at any viewport width, and that broader scope is resolved by the same fix (see **Root Cause** and **Learnings**).

**Resolved:**
- Closing a toast below the 767px breakpoint dispatches `onToastClose` and `toast-close` exactly once — fixed via the `composedPath()` check in `setOnClick()` plus the `visible` re-entry guard in `closeToast()`/`fadeOutToast()`; verified with a dedicated regression test that fails against the pre-fix source and passes with the fix.
- The untracked `setTimeout` in `fadeOutToast()` is tracked and cancelled if the toast is already closing/closed — added the `closeTimer` field, stored and cleared consistently across `clickToClose()`, `closeToast()`, `disconnectedCallback()`, and the `variant`-change branch of `updated()`. This is also what fixes the width-independent race (manual close during auto-hide fade-out at any screen size), which the ticket didn't originally call out but the same fix resolves.
- `closeToast()` guards against re-entry — added an early return when `this.visible` is already `false`; also verified directly against three sequential calls to `closeToast()` (only the first dispatches).
- New WTR unit tests cover a close-button click at a mobile-width viewport (added a test stubbing `window.innerWidth` via `sinon`, asserting both `onToastClose` and `toast-close` fire exactly once) **and**, following further review, a close-button click mid-fade at a desktop-width viewport (1200px) — added to `test/auro-toast.test.js` under "auto-hide timer lifecycle", independently verified to fail against the pre-fix source and pass with the fix.

## Learnings

- A regression test that passes is not proof of a fix — verify it by reverting the fix and confirming the test then fails, not just by reasoning about the code path.
- Fixing a review nit ("clear this timer too, for consistency") can silently introduce a new bug if the timer being cleared has a required side effect (here, a CSS class toggle) that isn't undone alongside it.
- Adding a lifecycle teardown hook (`disconnectedCallback`) without checking for a matching setup/re-arm counterpart (`connectedCallback`) can permanently and silently disable timer-driven behavior after a reconnect.
- Root-causing via `event.composedPath()` (discriminate the actual click source) is more robust than a state-guard alone, and can close latent races the state guard can't.
- Running a second, independent code review pass after implementing a first review's follow-up recommendations caught two additional regressions that the full test suite passing did not surface — worth treating "address the follow-ups" as new work requiring its own review, not a formality.
- A defect's initially-reported reproduction conditions (here, "mobile-width only") describe where it was *first observed*, not necessarily its actual scope — the fix's own tracked-timer mechanism turned out to be width-independent, but the test coverage and post-mortem narrative lagged behind that until a later review pointed it out. Scope test coverage and documentation to the root cause, not just the first trigger that surfaced it.

## Iterations That Didn't Work

- The first version of the mobile regression test declared the toast with `disableautohide`, which caused `fadeOutToast()`'s `!this.disableAutoHide` check to short-circuit before ever reaching the new `visible` guard — making the test vacuous (it passed against both the fixed and unfixed source). Caught by code review; fixed by removing `disableautohide` from the test fixture.
- Clearing `this.closeTimer` in the `variant`-change branch of `updated()` (added to mirror the existing `fadeOutTimer` clear, for consistency) left the toast container with the `.hidden` class applied but `this.visible` still `true` whenever a variant change interrupted an in-progress fade-out — the toast became permanently invisible with no close event ever dispatched. Fixed by also removing the `.hidden` class in that branch.
- Adding `disconnectedCallback()` to clear pending timers (intended to prevent a timer leak on unmount) broke auto-hide entirely for any toast disconnected and later reconnected to the DOM, since Lit's `updated()` lifecycle does not re-run on reconnect alone. Fixed by extracting a `_scheduleAutoHide()` helper and calling it from `connectedCallback()` in addition to `updated()`.
