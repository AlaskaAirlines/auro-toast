# AB#1643472

## Executive Summary

Tapping the "close" button on a toast notification could silently tell the app it had been closed *twice* instead of once, about a third of a second apart. This was first reported on phones and other narrow screens, but further review found the same double-notification could also happen on a normal desktop-sized screen, if the close button was tapped while a toast was in the middle of automatically fading away on its own. A further review pass found a related but opposite problem: a toast that was temporarily removed from the page while mid-fade (for example, during a framework re-render) could come back permanently invisible instead — stuck on screen with no way to close it and no close notification ever sent — if it reappeared as an error-type toast, or with auto-hide turned off. Most of the time none of this was visible to guests, but any feature reacting to a toast closing (analytics logging, removing an item from a list, re-enabling a button) could run twice for a single close, or never run at all. This change makes closing a toast — at any screen size, however it's closed, and even if it's briefly removed from the page mid-close — behave correctly every time: closed once, and only once, with no toast ever left permanently stuck. See [AB#1643472](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1643472).

## The Problem

Below a certain screen width (roughly phone- and small-tablet-sized), auro-toast has always let a guest dismiss a toast by tapping anywhere inside it, not just the close button — a convenience for touch devices. That convenience feature was not aware that a tap could also land on the dedicated close button, which already has its own, independent way of closing the toast. So a single tap on the close button, on a narrow screen, triggered both closing mechanisms at once — one instantly, and one about 300 milliseconds later.

Separately — and at **any** screen width, not just narrow ones — every toast that auto-hides fades itself out over roughly a third of a second before it actually closes. If a guest manually clicked the close button during that fade-out window, the close button's own immediate close and the fade-out's own scheduled close could both go on to fire, again about 300 milliseconds apart. This second path has nothing to do with screen width; it reproduces on a full-size desktop screen just as easily as on a phone. Either way, any code elsewhere in an app that listens for "the toast was closed" would hear about it twice.

A third, related problem surfaced during a later review of the fix itself. If a toast was removed from the page while it was still fading itself out — for example, a surrounding page re-rendering and briefly detaching the toast — and it was later reconnected to the page as an error-type toast, or with auto-hide turned off, the toast could come back permanently invisible. It never actually finished closing, so the "toast was closed" notification other code depends on was never sent either — the toast was simply stuck, silently, with no way out.

## Root Cause

Two distinct causes were present in `src/auro-toast.js` as originally shipped; a third was introduced — and resolved — as a self-inflicted intermediate step of this same fix, not a pre-existing production defect. All three stem from the same class of gap: pieces of the fade-out/close/reconnect lifecycle that weren't tracked or fully restored.

1. **Width-independent race (any viewport), present in shipped code:** `fadeOutToast()` is also how the auto-hide timeout closes a toast — after the auto-hide delay elapses, it adds a `.hidden` CSS class and originally scheduled the close 300ms later via an **untracked** `setTimeout` whose id was never stored, so nothing could cancel it once scheduled. If a guest clicked the close button during that 300ms window, `clickToClose()` closed the toast immediately, but had no way to cancel the still-pending, unstored timer — which fired `closeToast()` a second time regardless of width.
2. **Mobile-only compounding cause (<767px), present in shipped code:** below the mobile breakpoint, a host-level `onclick` handler installed by `setOnClick()` (to let guests tap anywhere on the toast to dismiss it) also called `fadeOutToast()`. Because the close button lives in a shadow DOM and its click event is `composed`/bubbling, a tap on the close button triggered `clickToClose()` (button-level listener) *and* bubbled up to this host `onclick`, which scheduled a second untracked close via the same unstored-timer gap as above — on top of the width-independent race, not instead of it.
3. **Reconnect-after-detach doesn't restore visual state — introduced and fixed within this same change, never shipped (any viewport, only on a mid-fade disconnect/reconnect):** `disconnectedCallback()` did not exist before this fix; it was added in an earlier pass of this same change (see **Why This Works**, pass 2) specifically to cancel the pending `closeTimer` when a toast is removed from the DOM mid-fade, so a detached toast can't fire a close on a node no longer in the document. That cancellation is correct on its own, but it left the `.toastContainer`'s `hidden` CSS class in place — added earlier by `fadeOutToast()` — with nothing left to remove it. On reconnect, `connectedCallback()` re-arms auto-hide via `_scheduleAutoHide()`, but that helper only schedules a *new* fade-out timer when the toast is still eligible to auto-hide (visible, not `disableAutoHide`, and not an error variant). If any of those conditions no longer held by the time the toast reconnected, no new timer was ever scheduled — and with it, nothing left to ever remove the leftover `hidden` class. The toast stayed permanently invisible even though `visible` was still `true`. Unlike causes 1 and 2, this was caught and fixed within this same change set before merge (see **Iterations That Didn't Work**) — it was never in shipped code.

All three causes trace back to timer- or state-cleanup gaps in the same fade-out/close/reconnect lifecycle. Fixing the timer-tracking gap (below) resolves the first two; restoring the container's visual state unconditionally on reconnect resolves the third.

## The Fix

- Added a tracked `closeTimer` field (previously the `fadeOutToast()` → `closeToast()` delay was an anonymous, unstored `setTimeout`), cleared alongside `fadeOutTimer` in `clickToClose()`, `closeToast()`, `disconnectedCallback()`, and the `variant`-change branch of `updated()`.
- `closeToast()` now guards against re-entry: it returns immediately if the toast isn't currently `visible`, so a second call (from any source) after the toast has already closed is a no-op.
- `fadeOutToast()` only proceeds (adds the `.hidden` class, schedules a close) if the toast is still `visible`.
- Root-caused the mobile double-close directly: `setOnClick()`'s host-level handler now inspects `event.composedPath()` and does nothing if the click originated on the close button — `clickToClose()` already owns that case, so the tap-to-dismiss handler no longer runs at all for close-button taps, rather than relying solely on the `visible` state guard to suppress the resulting duplicate.
- Added `disconnectedCallback()` to clear both timers on unmount, so a detached toast can't fire a delayed close on a node no longer in the document.
- Extracted a `_scheduleAutoHide()` helper (called from both `connectedCallback()` and `updated()`) so the auto-hide countdown correctly re-arms if a toast is disconnected and later reconnected (e.g. re-parented elsewhere in the DOM) — `updated()` alone does not re-run on reconnect, since no reactive property changes as a result.
- Cancelling a pending fade-out on a `variant` change now also removes the `.hidden` class from the toast container, so an interrupted fade doesn't leave the toast stuck invisible while still marked `visible`.
- `connectedCallback()` now unconditionally clears the toast container's `hidden` class *before* calling `_scheduleAutoHide()`, restoring full visibility on every reconnect regardless of whether a new auto-hide timer ends up being scheduled — so a toast disconnected mid-fade can never come back stuck invisible.

## Why This Works

The fix was arrived at over six review passes, each independently verified rather than trusted on inspection:

1. **Initial fix** (timer tracking + re-entry guard + `composedPath()` root cause) was paired with a regression test simulating a mobile-width close-button tap. A code review agent (dual-model, opus + sonnet) caught that the test used the `disableautohide` attribute, which made `fadeOutToast()` short-circuit *before* reaching the new `visible` guard — the test passed even against the unfixed source. This was confirmed empirically (reverting the source fix made the test fail as expected; restoring it made the test pass), not just reasoned about, and fixed by removing `disableautohide` from the test fixture.
2. **Follow-up hardening** (from the same review's recommendations): added `disconnectedCallback()` timer cleanup, the `composedPath()` root-cause fix, and replaced a brittle `Object.defineProperty(window, "innerWidth", ...)` test stub with a proper `sinon.stub(window, "innerWidth").get(...)` that correctly restores the original accessor.
3. **A second review pass** (also dual-model, high effort) on that follow-up work caught two *new* regressions it had introduced: clearing `closeTimer` on a `variant` change without undoing the `.hidden` class (a permanently stuck, invisible toast), and adding `disconnectedCallback()` without a matching re-arm in `connectedCallback()` (auto-hide permanently disabled after any reconnect). Both were fixed, covered with new regression tests, and each test was individually verified to fail against the pre-fix code and pass against the fix — the same discipline applied the first time.
4. **A human review pass** correctly challenged the scope of the fix itself: the double-dispatch was documented (both in this file and the original ticket) as mobile-width-only, but the reviewer had independently reproduced it at desktop width via a close-button click during the auto-hide fade-out, and by calling `closeToast()` three times directly. Both scenarios were re-verified from scratch against this fix — new tests for each were confirmed to fail against the pre-fix source and pass against the fix — before concluding the already-committed fix covered them (the same `closeTimer` tracking and re-entry guard happen to be width-independent, even though the accompanying test coverage at the time was mobile-only). This file's scope was corrected accordingly.
5. **A fifth review pass** (dual-model, high effort, run against the working tree before this batch of changes was committed) found that pass 3's `connectedCallback()` re-arm only rescheduled a *new* fade-out timer — it never independently restored the container's `hidden` class. A toast disconnected mid-fade and reconnected while `disableAutoHide` was `true`, or as an error-variant toast, would come back permanently invisible with no close ever fired. Fixed by having `connectedCallback()` clear the `hidden` class directly, decoupled from whether a new auto-hide timer ends up being scheduled. A dedicated regression test detaches a toast mid-fade, confirms no close fires while it's detached, then reconnects it and asserts the container is no longer hidden.
6. **A sixth review pass** — a full multi-model code review (opus + sonnet, high effort) of the completed PR — found **zero blocking issues** from either model, corroborating the fix. It surfaced four further single-model observations, none corroborated by both models and none blocking: two additional narrow timer/lifecycle edge cases (no `isConnected` guard on a timer re-arm while detached mid-fade; `closeTimer` not cleared if `visible` flips back to `true` within the 300ms fade window), a note that `_scheduleAutoHide()` restarts the full `timeTilHide` countdown on every reconnect rather than resuming elapsed time, and a documentation-accuracy nit on this file's Root Cause section (reworded above in response — `disconnectedCallback()` is introduced by this change, not pre-existing, and cause 3 was a self-inflicted intermediate regression rather than a shipped defect). A test-flake risk was also flagged in the pass-5 disconnect/reconnect regression test (it uses a real 50ms timer, unlike its two sibling tests which use `sinon.useFakeTimers()`). The timer/lifecycle edge cases are tracked as follow-up work under [AB#1646998](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1646998); the test-flake risk was left for a future pass.

The `composedPath()` approach is preferred over relying solely on the `visible` state guard because it removes the double-invocation at its source (the host handler never runs for close-button clicks) rather than suppressing a symptom of it — which also closes a latent race where a consumer's `toast-close` listener synchronously re-showing the toast could have defeated a state-only guard.

## Outcome

Closing a toast — however it's closed, and at any screen size — now notifies the rest of the app exactly once. This covers both the originally-reported mobile close-button tap and a second, independently-discovered desktop-width case (closing manually during the auto-hide fade-out). Toasts also no longer get stuck permanently invisible if their severity/type changes while they're in the middle of fading out, or if they are briefly detached from the page and reconnected mid-fade — and they continue to auto-dismiss correctly even if a toast is moved to a different part of the page while visible.

## Ticket Completeness

4 of 4 acceptance criteria resolved. The ticket itself was scoped to the mobile-width (<767px) symptom; a subsequent review correctly identified that the same underlying untracked-timer defect also reproduces at any viewport width, and that broader scope is resolved by the same fix (see **Root Cause** and **Learnings**). A later review pass also found and fixed an additional, related gap — a toast could stay permanently invisible after being detached and reconnected mid-fade — which the ticket didn't call out but is resolved by this same set of changes. A final multi-model review of the completed PR found no issues affecting any of these four criteria; it surfaced further narrow timer-lifecycle edge cases outside this ticket's scope, tracked separately under AB#1646998.

**Resolved:**
- Closing a toast below the 767px breakpoint dispatches `onToastClose` and `toast-close` exactly once — fixed via the `composedPath()` check in `setOnClick()` plus the `visible` re-entry guard in `closeToast()`/`fadeOutToast()`; verified with a dedicated regression test that fails against the pre-fix source and passes with the fix.
- The untracked `setTimeout` in `fadeOutToast()` is tracked and cancelled if the toast is already closing/closed — added the `closeTimer` field, stored and cleared consistently across `clickToClose()`, `closeToast()`, `disconnectedCallback()`, and the `variant`-change branch of `updated()`. This is also what fixes the width-independent race (manual close during auto-hide fade-out at any screen size), which the ticket didn't originally call out but the same fix resolves.
- `closeToast()` guards against re-entry — added an early return when `this.visible` is already `false`; also verified directly against three sequential calls to `closeToast()` (only the first dispatches).
- New WTR unit tests cover a close-button click at a mobile-width viewport (added a test stubbing `window.innerWidth` via `sinon`, asserting both `onToastClose` and `toast-close` fire exactly once), a close-button click mid-fade at a desktop-width viewport (1200px), a tap-anywhere-to-dismiss click on the message body at a mobile-width viewport, and a detach-mid-fade/reconnect scenario asserting no close fires while detached and full visibility is restored on reconnect — each independently verified to fail against the pre-fix source and pass with the fix.

## Learnings

- A regression test that passes is not proof of a fix — verify it by reverting the fix and confirming the test then fails, not just by reasoning about the code path.
- Fixing a review nit ("clear this timer too, for consistency") can silently introduce a new bug if the timer being cleared has a required side effect (here, a CSS class toggle) that isn't undone alongside it.
- Adding a lifecycle teardown hook (`disconnectedCallback`) without checking for a matching setup/re-arm counterpart (`connectedCallback`) can permanently and silently disable timer-driven behavior after a reconnect.
- Re-arming *one* side effect of an interrupted operation (a timer) on reconnect doesn't guarantee every side effect gets restored — a CSS class toggled imperatively, outside Lit's reactive render, needed its own explicit reset, decoupled from whether a new timer happened to get scheduled.
- Root-causing via `event.composedPath()` (discriminate the actual click source) is more robust than a state-guard alone, and can close latent races the state guard can't.
- Running a second, independent code review pass after implementing a first review's follow-up recommendations caught two additional regressions that the full test suite passing did not surface — worth treating "address the follow-ups" as new work requiring its own review, not a formality. A fifth pass, run again after the fourth's scope correction, caught yet another regression in the same lifecycle code — this class of fix (timer + imperative DOM state, disconnect/reconnect) appears to warrant review on every touch, not just the first.
- A defect's initially-reported reproduction conditions (here, "mobile-width only") describe where it was *first observed*, not necessarily its actual scope — the fix's own tracked-timer mechanism turned out to be width-independent, but the test coverage and post-mortem narrative lagged behind that until a later review pointed it out. Scope test coverage and documentation to the root cause, not just the first trigger that surfaced it.
- A documented lesson doesn't inoculate against repeating it: a new test written for this pass (tap-anywhere-to-dismiss on mobile) was first declared with the same `disableautohide` mistake this file's Iterations section already called out from an earlier pass. Rerunning the suite — not just remembering the lesson — is what caught it.
- A review that finds zero blocking issues still adds value: the final multi-model review of this completed PR corroborated the fix with no 🔴 findings, but still caught a documentation-accuracy gap in this very file — Root Cause #3 had blurred the line between an original shipped defect and a self-inflicted regression introduced and fixed within the same change — plus several narrow edge cases worth tracking that neither model alone would have surfaced.

## Iterations That Didn't Work

- The first version of the mobile regression test declared the toast with `disableautohide`, which caused `fadeOutToast()`'s `!this.disableAutoHide` check to short-circuit before ever reaching the new `visible` guard — making the test vacuous (it passed against both the fixed and unfixed source). Caught by code review; fixed by removing `disableautohide` from the test fixture.
- Clearing `this.closeTimer` in the `variant`-change branch of `updated()` (added to mirror the existing `fadeOutTimer` clear, for consistency) left the toast container with the `.hidden` class applied but `this.visible` still `true` whenever a variant change interrupted an in-progress fade-out — the toast became permanently invisible with no close event ever dispatched. Fixed by also removing the `.hidden` class in that branch.
- Adding `disconnectedCallback()` to clear pending timers (intended to prevent a timer leak on unmount) broke auto-hide entirely for any toast disconnected and later reconnected to the DOM, since Lit's `updated()` lifecycle does not re-run on reconnect alone. Fixed by extracting a `_scheduleAutoHide()` helper and calling it from `connectedCallback()` in addition to `updated()`.
- The new tap-anywhere-to-dismiss regression test was first written with `disableautohide` on its fixture — the exact same mistake as the very first bullet in this section, made again on a later pass. It failed for the wrong reason (0 close events, because `fadeOutToast()` never got past its `disableAutoHide` guard, not because the click handler was broken). Caught immediately by running the suite; fixed by removing `disableautohide`, matching what the code path under test actually requires.
