# AB#1376974

## Executive Summary

[AB#1376974](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1376974)

Developers using `auro-toast` inside Svelte applications could not attach a normal close handler: the component's close notification was named `onToastClose`, and Svelte automatically prepends its own `on` when binding to an event, forcing an awkward doubled `ononToastClose` handler name that most developers would never think to write. The component now also dispatches a second, standards-named `toast-close` event on every close, which binds normally in Svelte and other frameworks; the original `onToastClose` event keeps firing so existing consumers are not broken. While making this change, the component's machine-readable API manifest (`custom-elements.json`) was also published for the first time, and its property/attribute/event descriptions were corrected so IDE autocomplete and design-system tooling describe the component accurately. A code review of this work caught an in-flight regression — the deprecated `onToastClose` event's payload briefly changed shape as a side effect of an unrelated cleanup commit — which was corrected before merge (see **Ticket Completeness** below). A separate, pre-existing double-dispatch defect on mobile-width screens was also surfaced by the review and remains open as follow-up work.

## The Problem

Support reported that a Svelte application could not reliably react to a toast closing. The toast component announced its own closing by firing a notification named `onToastClose`. Svelte treats any handler name starting with `on` as its own event-binding convention and automatically adds another `on` in front of whatever name a developer supplies — so to catch this particular notification a Svelte developer would have had to write the confusing, undiscoverable name `ononToastClose`. In practice this made the close notification unusable in Svelte, and was an unpleasant surprise waiting for any other framework with similar conventions.

## Root Cause

In `src/auro-toast.js`, `closeToast()` dispatched a single `CustomEvent` named `"onToastClose"`. Svelte's `on:` directive itself prepends `on` to whatever event name it's given, so binding to an event whose name already starts with `on` produces a doubled `on` — this is a naming collision with Svelte's binding convention, not a defect in Svelte or in `CustomEvent` itself. Native and standard custom DOM events avoid this entirely by using plain, lowercase, non-`on`-prefixed names (`click`, `change`, `toast-close`).

Separately, and not the ticket's stated problem, the component's `custom-elements.json` manifest — used by IDEs and design-system tooling, not by the browser at runtime — was never published, and three properties (`disableAutoHide`, `noIcon`, `timeTilHide`) had no explicit `attribute:` key in `static get properties()`. This is a tooling-accuracy gap, not a runtime bug: Lit already derives the HTML attribute name as the lowercased property name by default (verified directly against `@lit/reactive-element`'s `__attributeNameForProperty`, which falls back to `name.toLowerCase()`), so `<auro-toast disableAutoHide>` was already being bound correctly at runtime before this change. What the missing `attribute:` key actually caused was the CEM static analyzer — which cannot see Lit's runtime default — emitting an inaccurate camelCase attribute name into the manifest that tooling consumes.

## The Fix

- **Added a `toast-close` event dispatch** in `closeToast()`, alongside the existing `onToastClose` dispatch, so both fire on every close path (close-button click, mobile tap-to-dismiss, and the auto-hide timeout) — `toast-close` does not start with `on`, so it binds normally in Svelte and other frameworks.
- **Deprecated `onToastClose`** via `@deprecated` JSDoc and an updated class-level `@fires` declaration, so it keeps firing during a migration window.
- **Added explicit `attribute` keys** to the three affected Lit property definitions, so the CEM manifest reports the same lowercase attribute names Lit was already binding to at runtime:
  - `noIcon` → `attribute: "noicon"`
  - `disableAutoHide` → `attribute: "disableautohide"`
  - `timeTilHide` → `attribute: "timetilhide"`
- **Added inline `/** @type */` JSDoc** above each property definition in `static get properties()`, replacing the removed class-level `@attr` tags.
- **Changed `variant`'s CEM type** from `{String}` to the union `{"error" | "success" | "custom"}`.
- **Published `custom-elements.json`**: removed it from `.gitignore`, added it to `package.json`'s `files` array so it actually ships in the npm tarball, and normalized the existing `"custom-elements"` package.json key from `"./custom-elements.json"` to `"custom-elements.json"`. (`package.json` already had a `"customElements": "custom-elements.json"` field before this change — that part was not missing, contrary to what an earlier draft of this document claimed.)
- **Updated `docs/api.md`** to the new auro-cli table format with the corrected lowercase attribute names, the new `toast-close` event, and the `register` method.

## Why This Works

A kebab-case, non-`on`-prefixed event name sidesteps Svelte's binding convention entirely and matches how native DOM events and other web-component libraries name custom events, so `toast-close` can be listened for with plain `addEventListener` or any framework's standard event-binding syntax. Declaring `attribute:` explicitly in `static get properties()` makes the CEM manifest agree with Lit's actual runtime behavior instead of relying on a fallback the static analyzer can't see. Dispatching both `onToastClose` and `toast-close` on every close, with `onToastClose`'s payload left untouched (`detail: this`), is what actually keeps existing consumers from breaking during the deprecation window — a follow-up commit was needed to restore this after it briefly regressed (see **Ticket Completeness** below).

## Outcome

`auro-toast` now fires a close event that can be bound normally from Svelte (and any other framework) without the doubled-`on` workaround, which was the reported problem. The component's manifest is now published and describes its attributes and events more accurately for IDE autocomplete and design-system tooling. The deprecated `onToastClose` event's payload regression flagged by code review (PR #147) was fixed before merge. One issue from that review remains open as follow-up work: the toast can dispatch both close events twice on mobile-width screens due to a pre-existing, previously-untested timing interaction that this change's new tests still don't cover.

## Ticket Completeness

4 of 5 acceptance criteria fully resolved; 1 partially resolved.

**Resolved**

- **A new close event whose name does not begin with `on` is dispatched on close** — `toast-close` is dispatched from `closeToast()` (`src/auro-toast.js`).
- **The new event can be bound with standard Svelte event syntax without a doubled `on` prefix** — `toast-close` does not start with `on`.
- **The existing `onToastClose` event continues to fire on close** — it dispatches on every close path.
- **"The existing `onToastClose` event continues to fire *unchanged*" / "Breaking change: None"** — Resolved, after a fix. A cleanup commit briefly changed `onToastClose`'s `detail` payload from the toast element itself (`detail: this`) to a plain object (`detail: { visible: this.visible }`), which would have silently broken any consumer reading a property off the old payload. Code review caught this before merge; the payload was restored to `detail: this` and the `toast-close` event was given its own `{ visible: false }` shape instead.

**Not Resolved / Partial**

- **"The event fires on every close path: close-button click, mobile tap-to-dismiss, and the automatic fade-out timer"** — Partially resolved. It does fire on all three paths, but on mobile-width viewports (under 767px) a close via the close button also triggers the host's own tap-to-dismiss handler through event bubbling, and an untracked `setTimeout` inside `fadeOutToast()` is not cancelled — so both events end up dispatched twice per close on mobile. This is a pre-existing latent defect that this change's new event doubles the impact of; it has no test coverage at any width below the 767px breakpoint, so it remains open as follow-up work. The related testing requirement ("New/updated WTR unit tests cover that both events fire on close, via the close button, mobile tap, and the auto fade-out timer") is correspondingly also only partially met — the close-button and auto-hide-timeout paths are tested for both events, but the mobile tap-to-dismiss path is not.

## Learnings

- **Verify a claimed runtime defect against the framework's actual source before writing the fix — and before writing the post-mortem.** The original root-cause draft claimed browsers "silently lowercase" attribute names, breaking camelCase attribute binding at runtime. Lit already lowercases undeclared attribute names by default (`__attributeNameForProperty` in `@lit/reactive-element`); there was no runtime binding defect. The real, valid problem was that the CEM static analyzer can't see that runtime default and needs an explicit `attribute:` key to describe it correctly.
- **Read the ticket's actual acceptance criteria before writing "The Problem."** The ticket's real complaint was about Svelte's `on`-prefix binding convention specifically, not general "web components should use kebab-case" style guidance. An earlier draft of this document never mentioned Svelte at all.
- **Check `git show <base>:<file>` before claiming a field "was missing."** `package.json` already had a `"customElements"` field before this change; the actual fix was adding the manifest file to the npm `files` array and normalizing an unrelated key. A post-mortem's Root Cause section should be checked against the pre-change file, not assumed from the diff alone.
- **"Both events fire, so nothing breaks" only holds if the payload is unchanged too.** Adding a new event alongside a deprecated one preserves compatibility only if the deprecated event's `detail` shape is untouched — changing it is a breaking change regardless of whether the event still fires.
- Web component custom events should use **lowercase kebab-case, non-`on`-prefixed** names (`toast-close`, not `onToastClose`) — this avoids collisions with framework-specific event-binding conventions (Svelte's `on:` in particular) as well as matching native DOM event style.
- **Use Lit's `attribute` key, not just JSDoc, to declare lowercase attribute names for CEM output.** Setting `attribute: "myattr"` in `static get properties()` makes the CEM manifest match Lit's runtime default; relying on `@attr` JSDoc alone only fixes documentation, not the manifest.
- New tests added specifically to catch a payload/behavior regression should be applied symmetrically to *all* affected events, including pre-existing ones whose contract also changed — not just the newly added event.

## Iterations That Didn't Work

- **Class-level `@attr` tags with lowercase names.** The initial approach was to change `@attr {Boolean} disableAutoHide` to `@attr {Boolean} disableautohide` in the class-level JSDoc block. This updated the CEM documentation but did not change Lit's `static get properties()` configuration. The correct fix is the `attribute: "disableautohide"` key in the property definition itself, which is what the CEM analyzer actually reads.
- **Duplicate JSON keys during `custom-elements.json` editing.** When patching the `variant` type with a `replace_all` edit, the replacement pattern added a new `type` key without removing the existing one, producing invalid JSON with two `type` keys in the same object. The fix required reading the affected block and replacing the whole duplicate entry.
