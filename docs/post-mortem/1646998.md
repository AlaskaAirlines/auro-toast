# AB#1646998

## Executive Summary

A previous fix to how auro-toast closes itself ([AB#1643472](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1643472)) resolved a bug where closing a toast could be reported twice. That fix's own final review turned up three smaller, related timing issues in the same area — none serious enough to hold up that earlier fix, but worth addressing on their own. This work resolves two of them: a toast that had been temporarily removed from the page could still end up closing itself while off-screen, and a toast element reused to display a new message (a common pattern for showing a stream of notifications efficiently) could inherit a leftover timer from its previous message and close unexpectedly a moment after being reused. The third issue — a toast restarting its full on-screen countdown every time it's reattached to the page, rather than picking up where it left off — was confirmed to be the intended, correct behavior and is now documented as such. See [AB#1646998](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1646998).

## The Problem

A toast's on-screen countdown could behave unexpectedly in a couple of circumstances that wouldn't show up under normal use. First, if the app briefly removed a toast from the page (for example, during a re-render) and, separately, some other unrelated setting on that toast changed while it was off-screen, the toast could end up timing itself out and reporting itself as closed while it was still detached — before the app ever got a chance to show it again. Second, some apps reuse a single toast element to display a stream of messages one after another, rather than creating a new one each time, to keep things efficient. If a new message was shown in place of an old one while that old message was still in the middle of fading away, the old message's leftover close timer could still go off and incorrectly close the new message roughly a third of a second later, for a reason that had nothing to do with the new message at all. A third, related question was also raised: should a toast that gets frequently reattached to the page keep restarting its full display countdown from the beginning each time, rather than remembering how long it had already been shown? That was reviewed and confirmed to be the correct, intended behavior.

## Root Cause

Both defects are gaps in the same class the prior post-mortem already called out: pieces of the fade-out/close/reconnect timer lifecycle that weren't tracked against every state transition that can affect them, only the ones the original fix's test coverage happened to exercise.

1. **No `isConnected` guard on timer re-arm:** `_scheduleAutoHide()`'s eligibility check considered `visible`, `disableAutoHide`, and `variant`, but never the toast's connection state. Lit calling `updated()` (and therefore `_scheduleAutoHide()`) does not require the element to be connected, so a property change processed while detached could arm a timer with no guarantee the toast would still be attached to the page — or even the same page context — by the time it fired.
2. **`closeTimer` untouched by a `visible: false → true` transition:** the set of places that clear `closeTimer` was scoped to the paths identified while fixing the original double-close bug — a user-initiated close, an auto-triggered close, an unmount, and a `variant` change mid-fade — not to every way a toast's close-in-progress state could become stale. Reusing an element for a new message via direct property assignment is a legitimate pattern that doesn't route through any of those four paths, so the stale timer had no path to cancellation.

The third observation from the prior review — `_scheduleAutoHide()` restarts the full `timeTilHide` countdown on every reconnect rather than resuming elapsed time — was confirmed to be intentional, not a defect. Restarting on reconnect is inseparable from `connectedCallback()` re-arming auto-hide at all: "visible for N ms" is scoped to a single connected mount, matching how a guest actually experiences the toast (a toast off-screen isn't accruing visible time), and a resume-elapsed-time model would require persisting and restoring an elapsed-time budget across disconnects — meaningful added complexity with no corresponding product requirement. This is now documented directly in `_scheduleAutoHide()`'s JSDoc so a future reader doesn't have to re-derive the same reasoning.

## The Fix

- `_scheduleAutoHide()`'s auto-hide eligibility check now also requires `this.isConnected`, so a property change processed while detached can never arm a timer that fires off-DOM. Reconnecting still re-arms it correctly, since `connectedCallback()` calls `_scheduleAutoHide()` again once the toast is actually connected.
- `updated()` now clears `closeTimer` and removes the toast container's `hidden` class whenever `visible` becomes `true`, so a reused toast element can never inherit a stale close timer or leftover hidden state from a previous message's fade-out.
- Documented, via a JSDoc comment on `_scheduleAutoHide()`, that restarting the full countdown on every reconnect (rather than resuming elapsed time) is intentional, and why — closing out the third edge case without a behavior change.

## Why This Works

Both source changes were verified the same way the originating PR's fixes were: each new regression test was confirmed to fail against the pre-fix source and pass with the fix, not just reasoned about.

- The `isConnected` guard test detaches a toast, then changes an unrelated reactive property (`noIcon`) while detached — reproducing "a reactive property change while disconnected" without depending on any particular framework's remount timing — and asserts no close ever fires. Run against the pre-fix source, `_scheduleAutoHide()` re-arms a new timer that fires ~50ms later regardless of connection state, so the test fails as expected (`toast-close` count 1, not 0); with the `isConnected` check added, it passes.
- The stale-`closeTimer` test lets a toast begin fading out (`clock.tick(50)`, past `timeTilHide`, confirming the container has `hidden` applied), then simulates reuse by toggling `visible` directly (`false` then `true`, bypassing `clickToClose()`/`closeToast()`/`disconnectedCallback()` entirely, matching how a message-queue consumer would actually reuse the instance), and asserts both that the leftover `hidden` class is removed and that advancing past the original 300ms fade window never closes the reused toast. Against the pre-fix source this fails on the first assertion (the `hidden` class survives the reuse); with the fix, `updated()`'s new `visible`-became-`true` branch clears both the class and the stale timer.

No test was added for the third (documentation-only) item, since no runtime behavior changed — the existing reconnect/re-arm coverage from AB#1643472 already exercises `_scheduleAutoHide()` being called on reconnect.

## Outcome

A toast can no longer arm an auto-hide timer that fires while it's disconnected from the page, and a toast element reused for a new message can no longer inherit a stale close timer or leftover hidden visual state from whatever message previously occupied that instance. The reconnect-restarts-the-countdown behavior is now explicitly documented as intentional, closing out the last of the three edge cases the AB#1643472 review surfaced without introducing elapsed-time-tracking complexity that had no corresponding product ask.

## Ticket Completeness

3 of 3 requirements from the ticket resolved.

**Resolved:**
- No connection-state guard on the auto-hide timer — a toast can no longer restart its on-screen countdown while it isn't actually attached to the page, so it can never close itself while off-screen; covered by a dedicated regression test.
- Leftover close timer not cleared when a toast is reused for a new message — a toast reused mid-fade-out now has its leftover timer and hidden visual state cleared before the new message is shown; covered by a dedicated regression test.
- Whether a toast should restart its full display countdown every time it's reattached to the page, rather than resuming where it left off — confirmed as the intended, correct behavior and documented as such in code, per the ticket's own framing ("possibly intended behavior, but worth confirming and documenting either way").

## Learnings

- A review that finds zero blocking issues can still surface real, worth-fixing gaps — this ticket exists because the AB#1643472 review explicitly deferred non-corroborated, non-blocking findings to follow-up rather than either ignoring them or blocking the original PR on them. Tracking them separately kept the original PR scoped while not losing the findings.
- "No `isConnected` guard" is a distinct failure mode from the disconnect/reconnect races the original fix covered — those were about *cancelling* timers on disconnect and *restoring* state on reconnect; this one is about *never arming* a new timer while disconnected in the first place. Timer-lifecycle bugs in the same function can require guards at multiple, non-overlapping points (arm-time eligibility vs. cancel-on-teardown vs. restore-on-reconnect).
- An item hedged in its own ticket description ("possibly intended behavior") doesn't always need a behavior change to be resolved — confirming the reasoning and writing it down is itself a valid fix when the alternative (resume-elapsed-time tracking) would add real complexity against no concrete product requirement.

## Iterations That Didn't Work

None — both source fixes and their regression tests were verified against the pre-fix source on the first attempt.
